# Deploy EasyOats for multiple users

This deployment uses one Streamlit web service, one managed PostgreSQL database, Google or Microsoft OpenID Connect sign-in, and a persistent disk for the generated Excel report and its backups. Every device opens the same HTTPS address and reads/writes the same PostgreSQL data.

## What has already been prepared

- `DATABASE_URL` selects PostgreSQL without changing application code.
- Alembic applies versioned database migrations from `migrations/`.
- `scripts/migrate_sqlite_to_postgres.py` creates a consistent SQLite backup, refuses a target with operational activity, safely replaces untouched first-boot defaults, copies every record in one target transaction, preserves IDs, resets PostgreSQL sequences, and verifies row counts.
- Hosted mode uses Streamlit OIDC. Only active accounts in `app_users` can enter.
- Roles are `staff` and `admin`. Administrators can maintain the allowlist and perform audited stock overrides. Staff cannot change access permissions.
- `deployment/start.py` validates secrets, applies migrations, initializes the durable Excel workbook, and starts Streamlit.
- `render.yaml` provisions the web service, managed PostgreSQL, HTTPS endpoint, health check, and persistent workbook disk.

## 1. Put the project in a private GitHub repository

Create a private repository and push this project. Verify that `.env`, databases, generated Excel files, and backups are absent from the commit. The read-only deployment template at `templates/EasyOats_Order_Tracker.xlsx` is intentionally included.

Do not upload `.streamlit/secrets.toml`. Hosted startup creates it from protected environment variables.

## 2. Create a Google OIDC client

In Google Cloud Console:

1. Create or select a project.
2. Configure the OAuth consent screen for your organization or selected test users.
3. Create an **OAuth client ID** with application type **Web application**.
4. Add this authorized redirect URI, replacing the hostname with the final Render service URL:

   ```text
   https://easyoats-order-manager.onrender.com/oauth2callback
   ```

5. Save the client ID and client secret. Do not place either in Git.

Microsoft Entra ID can be used instead. Set its OIDC metadata URL and register the same `/oauth2callback` redirect URI.

## 3. Create the Render Blueprint

1. Sign in to Render and choose **New → Blueprint**.
2. Connect the private GitHub repository.
3. Select the repository's `render.yaml`.
4. During creation, enter these protected values:

   | Variable | Value |
   | --- | --- |
   | `OIDC_REDIRECT_URI` | Final HTTPS URL ending in `/oauth2callback` |
   | `OIDC_CLIENT_ID` | Client ID from Google/Microsoft |
   | `OIDC_CLIENT_SECRET` | Client secret from Google/Microsoft |
   | `BOOTSTRAP_ADMIN_EMAILS` | Your work email; comma-separate recovery administrators |
   | `BOOTSTRAP_STAFF_EMAILS` | Optional initial staff emails, comma-separated |

   `AUTH_COOKIE_SECRET` is generated by Render. `DATABASE_URL` is connected automatically to Render PostgreSQL.

5. Confirm that the web service has the `/var/data` persistent disk. Only files below this path survive deploys and restarts.

If Render changes the service hostname to avoid a name collision, update `OIDC_REDIRECT_URI` in Render and the authorized redirect URI in Google/Microsoft, then redeploy.

## 4. Transfer existing local records

Do this before the team starts entering records in the hosted app. Close the local Streamlit window first so no order is added during transfer.

In Render, open the PostgreSQL database and copy its **external** connection URL. From PowerShell in this project folder:

```powershell
$env:TARGET_DATABASE_URL = Read-Host "Paste the Render PostgreSQL external URL"
.\.venv\Scripts\python.exe scripts\migrate_sqlite_to_postgres.py --dry-run
.\.venv\Scripts\python.exe scripts\migrate_sqlite_to_postgres.py
Remove-Item Env:TARGET_DATABASE_URL
```

The dry run only inspects the local source. The real run:

1. Creates a transactionally consistent backup in `backups/migrations/`.
2. Applies the current PostgreSQL schema.
3. Stops if the destination contains orders, feedback, audit activity, or changed first-boot settings. Untouched defaults from an initial web-service boot are safely replaced, while bootstrap login accounts are retained.
4. Copies settings, inventory, orders, feedback, synchronization state, audit history, and user access.
5. Verifies every copied row count before reporting success.

If the hosted database already has test records, create a fresh empty database instead of forcing the transfer over existing records.

## 5. Verify before inviting the team

Open the Render URL and sign in with the bootstrap administrator email. Check:

1. Dashboard totals match the local application.
2. Search finds an existing customer using a differently formatted number.
3. The newest order, payment state, inventory quantities, feedback, and audit history are present.
4. **الإعدادات والتصدير** downloads a valid Excel workbook.
5. Add one staff email under **حسابات الفريق وصلاحياته** and verify that account can sign in but cannot manage users or perform an administrator override.
6. Create a small test order, update it from a second device, confirm the first device sees it after refresh, then mark the test order cancelled.

Keep the local SQLite migration backup until these checks pass. After cutover, PostgreSQL is authoritative; do not continue entering production orders in the local application.

## Operations

- Add, suspend, or promote accounts from the hosted settings page. Keep at least two administrator emails for recovery.
- Review Render PostgreSQL backup/retention settings before launch. Periodically test a restore into a separate database.
- The persistent disk holds operational Excel copies, while PostgreSQL remains the source of truth.
- Use one web-service instance with the current Excel writer. PostgreSQL supports concurrent users, and the application serializes inventory-changing transactions. Horizontal web-service scaling should wait until Excel output is moved to shared object storage.
- Every deploy runs `alembic upgrade head` before the web server. Future schema changes should be delivered as additional Alembic revisions.
- To roll back the cutover, stop the hosted service, return users to the local app, and use the untouched SQLite backup. Reconcile any orders entered after cutover manually; the migration intentionally has no destructive reverse-sync command.

## Local development remains available

`run.bat` continues to use local SQLite and does not require cloud sign-in. To test OIDC locally, configure the variables in `.env`, change the provider redirect URI to `http://localhost:8501/oauth2callback`, and start through `deployment/start.py` with a PostgreSQL test database.
